# 참가자 라우터 (LPB Router)

`router-run` 진입점은 `src/ossp_router/lpb.py` 입니다.
런타임은 **Python 표준 라이브러리만** 사용하며, 학습에만 NumPy를 씁니다.

## 설계 요약

이 과제에서 등급 점수를 0으로 만드는 것은 라우팅 실패가 아니라 **비용 초과**입니다.
공개 Dev에서 `axk1-think` 의 문항당 비용은 all-light 기준선의 **22.6배**이고,
Fast 등급의 여유분은 전체의 0.25배뿐이라 승급 가능한 문항은 약 1%입니다.
주최측 `hash-regex` baseline 도 공개 Dev 3.985 → 채점셋 약 4.2 로 Premium 0점을
받았습니다(`baselines/README.md`). 그래서 순서를 비용 → 품질로 둡니다.

1. **크레딧이 아니라 토큰을 예측한다.** 입력·출력 토큰 수를 모델별로 로그공간에서
   회귀한 뒤, 공개된 단가로 비용을 조립합니다. 단가는 정확히 알려져 있고 불확실한
   것은 토큰 수뿐이기 때문입니다.
2. **Duan smearing 보정.** `axk1-think` 출력 토큰은 평균 3,185 / 중앙값 1,499 로
   꼬리가 두껍습니다. 로그 적합의 `exp()` 는 기하평균을 주는데 예산은 산술평균으로
   과금되므로, smearing 계수로 되돌립니다.
3. **배치 전체로 배분한다.** `docs/RUNTIME.md` 는 입력 전체를 한 번에 전달하고
   예산은 그 배치의 총합에 걸립니다. 문항마다 (비용, 점수) 의 상위 오목 포락선을
   만들고, **크레딧당 품질 이득**이 큰 승급부터 한도까지 사들입니다.
4. **여유는 초과분에만 적용한다.** all-light 는 정의상 1.0배라 초과할 수 없으므로
   위험한 것은 초과분뿐입니다. 총 한도에 계수를 곱하면 Fast(1.25배)는 가용 여유의
   대부분을 잃고 Premium(4.0배)은 조금만 잃어 — 가중치가 가장 큰 등급이 가장 크게
   손해 봅니다.
5. **외삽을 막는다.** 로그선형 적합은 학습 범위 밖에서 무한정 외삽합니다. 보정 전
   7만 자 프롬프트에서 `ax31-light` 의 출력 토큰이 **155만 개**(생성 조건 32,768의 47배)로
   예측됐고, 같은 프롬프트에서 `ax31` 은 **light 의 0.04배 비용**으로 나왔습니다.
   그러면 배분기가 "공짜 승급"을 무한히 사들입니다. 두 가지로 막습니다.
   - 예측 토큰 수를 **학습에서 관측된 범위로 클램프**
   - 공개 단가 사다리(`ax31-light` < `ax31` < `axk1-think`)를 따라
     **비싼 모델이 싼 모델보다 싸게 예측되지 않도록 하한**을 겁니다.
     공개 Dev 실측에서 `ax31` 이 `ax31-light` 보다 싼 경우는 0.35%, `axk1-think` 는 0건입니다.
6. **점수 예측은 2PL 문항반응모형.** `p_m = sigmoid(a_m · (θ(x) − b_m))`,
   프롬프트 능력 `θ(x)` 는 공유하고 모델마다 파라미터 2개만 둡니다.
   독립 회귀 3개와 grouped 5-fold CV 를 fold 시드 3개로 비교했을 때 3/3 에서
   앞섰고, 시드 간 변동폭이 **0.0011 대 0.0230** 이었습니다. 비공개 평가셋의
   구성이 공개되지 않는 과제에서는 평균보다 이 안정성이 중요합니다.

## 마진 산정 — Premium 이 예산을 다 못 쓰던 문제

한때 Premium 은 한도 4.0 중 **2.66** 만 쓰고 끝났다. 원인을 셋으로 나눠 확인했다.

1. **배분기가 살 것이 없어서인가?** 아니다. excess 를 올리면 `axk1-think` 선택이
   52 → 611 개까지 계속 늘어난다. 포화가 아니다.
2. **비용 모델이 과대 예측해서인가?** 반대다. `axk1-think` 를 **20% 과소** 예측했다.
3. **마진을 배포보다 나쁜 예측기로 쟀기 때문이다.** ← 이것이 원인.

세 번째가 핵심이다. 배포 예측기는 Train **전체**로 적합되는데, 마진은 5-fold
out-of-fold 예측으로 쟀다. 80% 로 적합한 모델은 더 시끄럽고, 시끄러운 점수 모델은
**나쁜 승급을 산다**. `axk1-think` 가 light 대비 22배이므로 그 오구매는 비싸다.
같은 마진에서 out-of-fold 는 Train 에서 비율 **3.29** 를 썼는데 배포 모델은 같은
문항에서 **2.37** 을 썼다. 그 격차만큼 마진이 과도하게 보수적이 된 것이다.

두 가지를 고쳤다.

- **마진 산정 fold 를 12 로 올리고 2회 반복**했다 (`--margin-folds` / `--margin-repeats`).
  fold 모델이 Train 의 ~92% 를 보므로 배포 예측기에 가까워진다.
- **비용 보정 계수**를 out-of-fold 로 추정해 예측 비용을 불편(unbiased)으로 만들었다
  (`cost_calib`). 실측 보정값은 light ×1.018 · ax31 ×1.034 · **axk1-think ×1.240** 이다.
  smearing 은 표본 내 로그→선형 편향만 고치고, 표본 밖의 잔여 편향은 남는다.
  이 편향을 남겨 두면 **tier 마진이 보이지 않는 비용 편향까지 대신 흡수**하게 된다.

여기까지의 결과 (공개 Dev, held-out):

| | Premium 비율 | 한도 사용률 | Premium 점수 | 최종 |
| --- | ---: | ---: | ---: | ---: |
| 처음 | 2.658945 | 66.5% | 0.709659 | 0.679091 |
| 12-fold 마진 | 3.172569 | 79.3% | 0.719602 | 0.682244 |
| + 비용 보정 | 3.287861 | 82.2% | 0.720739 | 0.682472 |

### 그런데 그 여유는 안전하게 쓸 수 없었다

위 구성을 `redteam_harness` 의 혼합비 변화 스트레스(공개 Dev, 200회 재추출)에 넣자
**Balanced 초과 확률 10.5% · Premium 9.0%** 가 나왔다. 공개 Dev 한 번의 점수는
통과였지만, 비공개셋 구성이 조금만 달라지면 열 번에 한 번은 등급이 0점이 된다는 뜻이다.

그래서 마진 산정에 **혼합비 재추출 게이트**를 넣었다
(`ratio_quantile_under_shift`). Train 의 9개 대략 계열 비중을 Dirichlet 으로 다시 뽑아
가상 평가셋 60개를 만들고, 비용 비율의 **95분위수가 한도를 넘으면** 그 마진을 채택하지
않는다. 계열 라벨은 **학습기 안에서만** 쓰며 라우터에 전달되지 않는다.

게이트를 만들면서 내 시뮬레이션의 결함이 셋 나왔고, 전부 같은 방향으로 틀렸다 —
**위험을 과소평가**하고 있었다.

1. **템플릿 단위(1,516개)로 재추출하면 혼합비가 사실상 안 흔들린다.** 평범한
   부트스트랩과 구별되지 않아 초과 확률 0% 를 보고했다. 위험은 **계열 단위(9개)** 에 있다.
2. **반복 추출한 out-of-fold 예측을 평균내면 예측기가 배포보다 좋아진다.** 평균낸
   예측으로 재면 실제로 10~12% 초과하는 마진이 0% 로 보고됐다. 이제 반복마다 따로 재고
   **최악값**을 쓴다.
3. **"초과 확률 ≤ 2%" 라는 기준 자체가 추정 불가능했다.** 세계 60개에서 2% 는 1.2개다.
   그 추정치는 잡음이 지배하며, 실제로 Balanced 를 1.7% 로 보고했는데 독립 하네스가
   held-out Dev 에서 잰 값은 **10.5%** 였다. 이제 빈도가 아니라 **비율의 95분위수**를
   본다 — 같은 표본으로 훨씬 안정적으로 추정되고, 세 등급을 올바르게 갈라낸다.

### 분할 간 비용 구조 차이 (`--split-drift`)

계열 재추출을 고쳐도 Balanced 는 여전히 통과했다(Train p95 1.926 < 2.0). 그런데 Dev
실측 p95 는 **2.110** 이었다. 원인은 혼합비가 아니라 **분할 자체의 단가 구조**다 —
Dev 의 `ax31`/light 비용비는 **2.2468**, Train 은 **2.0915** 로 7.4% 높다. Balanced 는
거의 전부 `ax31` 이므로 그 차이가 그대로 비율에 실린다. Train 안에서 계열을 아무리
흔들어도 이 차이는 보이지 않는다.

그래서 분위수 기준에 **10% derate** 를 건다 (`--split-drift`, 기본 1.10):
`shift_p95 ≤ 한도 / 1.10`. 이것은 held-out 점수에 맞춘 값이 아니라 두 분할의
**단가 구조 차이(7.4%)** 에서 나온 선언적 상수다.

### 최종 마진과 대가

| 등급 | excess | Train oof 비율 | Train shift p95 | p95 상한 |
| --- | ---: | ---: | ---: | ---: |
| Fast | 0.25 | 1.102 | — | 1.136 |
| Balanced | 0.60 | 1.647 | 1.789 | 1.818 |
| Premium | 0.45 | 2.326 | 2.891 | 3.636 |

Premium 의 초과 곡선은 절벽이다 — excess 0.45 에서 p95 **2.891**, 0.50 에서 **3.669**,
0.55 에서 **4.087**. 절벽의 정체는 계열별 비용 예측 산포다: 보정 후에도 `axk1-think` 의
예측/실제가 계열마다 **0.56~1.63** 으로 흩어져 있고 `code-exec` 는 think 가 light 의
**150배**다. 그런 계열이 많은 세계가 뽑히면 몇 건의 승급만으로 한도를 넘는다.

기대값으로 보면 보수적 선택이 명확히 낫다. Balanced 를 0.60 → 0.75 로 올리면 Dev 품질이
약 +0.003 오르지만 등급 전체(최종의 0.3×0.69 ≈ 0.207)를 **10.5%** 확률로 잃는다 —
기대 손실 0.022 대 이득 0.003 이다.

### 검증 결과 (공개 Dev, 독립 하네스)

| 등급 | 수정 전 초과확률 | **수정 후** | p95 / 한도 |
| --- | ---: | ---: | ---: |
| Fast | 1.0~1.5% | **0.0~0.5%** | 1.137 / 1.25 |
| Balanced | **10.5~11.5%** | **2.5~3.0%** | 1.894 / 2.00 |
| Premium | 9.0~9.5% | **0.0%** | 2.605 / 4.00 |

혼합비 변화 하 최종 점수의 5분위수도 **0.468 → 0.624** 로 올라갔다. 공개 Dev 점수는
0.0028 내렸지만, 점수가 실제로 지켜질 확률이 크게 올랐다.

### 경험 분위수 → 모수적 꼬리 한계

경험 p95 는 **그 너머에서 무슨 일이 나는지 말해 주지 않는다.** Balanced 는 p95 가
1.894 로 한도 2.0 아래였는데도 2.5~3% 초과했다 — 초과분이 전부 추정 분위수 바깥에
있었다. 세계별 비율은 로그정규에 가까우므로 분위수 대신
**`exp(mean + z·sd)` (z=2.33, 상위 1%)** 로 바꿨다. 표본 전체로 추정되고,
**비율 분포가 넓은 등급을 자동으로 더 조이고 좁은 등급은 푼다.**

효과가 등급마다 반대 방향으로 나왔고 그것이 이 기준의 요점이다:

| 등급 | excess (경험 p95) | **excess (모수적)** | 방향 |
| --- | ---: | ---: | --- |
| Fast | 0.25 | 0.25 | 불변 |
| Balanced | 0.60 | **0.55** | 조임 |
| Premium | 0.45 | **0.50** | **풀림** |

균일 derate 로는 낼 수 없는 배분이다. 최종 점수는 0.676449 → **0.676619** 로 사실상
같지만 꼬리가 개선됐다 (Balanced p95 1.894 → 1.859, 최댓값 2.206 → 2.148).

### 미해결로 남기는 것

**Balanced 는 여전히 2.5% 로 세 등급 중 가장 취약하다.** 모수적 꼬리 한계가 꼬리 모양은
개선했지만 초과 세계 수는 80개 중 2개로 같다 — 이는 **측정 분해능(1/80 = 1.25%)과 같은
크기**라 실제로 줄었는지 말할 수 없다.

여기서 멈춘 이유는 기대값이 평평하기 때문이다. 2.5% 초과의 기대손실은
0.025 × 0.3 × 0.685 ≈ **0.005** 인데, 마진을 한 칸 더 조이면 Balanced 품질이 약 0.005
내려가 **0.0015** 를 잃는다. 순이득 0.003 은 이 측정의 잡음보다 작다.

구조적으로 Balanced 는 **light↔ax31 이진 배분**이고(think 선택 0건) 비율 변동은
`ax31`/light 비용비의 계열·분할 간 산포에서 온다. 그 산포는 아래 "계열별 비용 산포"
절에서 **줄일 수 없음이 확인**됐다. 즉 이 2.5% 는 마진 설계의 미완성이 아니라 비용
예측 한계가 남긴 잔여 위험이다.

균일 derate 의 형태 문제도 남는다 — 실측 분할 간 드리프트는 등급마다 다르다
(fast ×1.067 · balanced ×1.117 · premium ×1.181). 등급별 derate 면 맞출 수 있지만
그 상수는 공개 Dev 를 보고 정해야 하므로 하지 않았다.

**결론: Premium·Balanced 의 남는 여유는 실재하지만 안전하게 쓸 수 없다.** 안 쓰는
예산은 낭비가 아니라 비공개셋 구성을 모른다는 사실의 대가다. 이 값을 올리려면 마진이
아니라 **계열별 비용 예측 산포**를 줄여야 한다 — 그것이 남은 실질 개선 경로이고,
`word-math` 가 Dev 에서 0.555 로 가장 크게 과소 예측되는 단일 표적이다.

## 계열별 비용 산포 — 줄이려 했고, 줄지 않았다

마진을 묶는 것은 계열별 비용 예측 산포다. 그래서 줄여 보려 했고, **가설 네 개를 전부
측정으로 기각했다.** 결론부터: **이 데이터·이 특성에서 산포는 사실상 줄일 수 없다.**

### 왜 줄지 않는가 — 비용이 꼬리에 지배된다

`axk1-think` 비용의 상위 5% 문항이 전체의 **36.7%(Train) / 39.1%(Dev)** 를 차지한다.
`word-math` 는 **50.0% / 53.9%** 이고 gini 는 0.685 / 0.744 다. 출력 토큰의
out-of-fold 로그 잔차 표준편차는 **0.912**, 즉 문항별 예측은 **약 2.5배** 안에서만 맞는다.

계열 집계 편향은 "그 표본에 어떤 극단 문항이 들어왔는가"가 결정한다. 평균 모형을
아무리 잘 만들어도 이건 안 없어진다.

### 기각 1 — 계열별 보정

Train OOF 로 잰 계열별 보정 계수를 Dev 에 적용하면 산포가 **오히려 커진다**
(로그편향 sd **0.292 → 0.472**). Train↔Dev 상관은 pearson **+0.342** 뿐이고,
Train 추정치 자체의 산포(0.483)가 고치려는 대상(0.292)보다 크다. 최적 축소를 걸어도
0.292 → 0.274 로 6% 개선이 한계다. **채택하지 않는다.**

### 기각 2 — 승자의 저주(adverse selection) 보정

배분기가 **예측 비용**으로 밀도를 매기므로, 비용이 과소 예측된 문항을 우선 사들여
예산을 터뜨린다는 가설. 실측하니 반대였다 — 선택된 think 문항의 예측/실제는
**1.471(Train) / 1.028(Dev)** 로 오히려 **과대** 예측 쪽이다. 밀도 순위가 애초에
싼 문항을 선호하기 때문이다. **기전이 존재하지 않는다.**

(단 Dev 의 balanced `ax31` 에서는 선택분 0.954 vs 전체 1.035 로 약 8% 의 실제
adverse selection 이 있다. 크기가 작고 `--split-drift` 10% 가 이미 덮는 범위다.)

### 기각 3 — 더 좋은 평균 모형

`dim ∈ {512, 1024} × alpha ∈ {0.3, 1, 3, 10, 30}` 와 장황도 특성 12종을 추가해
out-of-fold 로 쟀다. 문항별 잔차 sd 는 **0.878~1.048** 사이에서만 움직였고 배포값
0.911 이 이미 최적 부근이다. **특성을 더 넣어도 천장이 움직이지 않는다.**

### 기각 4 — 계열 편향 산포를 목적함수로 삼기

이것이 가장 유익한 실패다. 스윕에서 축소를 줄이면(`alpha` 0.3~1) 계열 편향 산포가
**0.493 → 0.426** 으로 줄었다. 그래서 `--cost-alpha` 를 1.0 으로 낮춰 봤더니
**실제 점수는 내려갔다** (Dev 0.6764 → 0.6727, dim 1024 는 0.6686).

기전: 축소를 줄이면 계열 집계 편향은 줄지만 **문항별 예측이 나빠지고**(0.911 → 0.947),
나쁜 예측은 흔들린 세계에서 **나쁜 승급을 사서** shift p95 를 올린다. 그래서 Fast 마진이
0.25 → 0.15 → 0.05 로 무너졌다.

**교훈: 계열 편향 산포는 마진을 묶는 양의 대리변수가 아니었다.** 실제로 묶는 것은
문항별 예측 품질이다. 대리변수를 최적화하면 진짜 목적함수가 나빠질 수 있다.

### 실제 목적함수로 다시 재기

`--cost-alpha` 를 실제 Dev 최종 점수로 재면 1.0 → 0.6727 · **3.0 → 0.6764** ·
10.0 → 0.6779 · 30.0 → 0.6756 이다. 10.0 이 명목상 +0.0014 앞서지만 **채택하지
않는다**: ① 4점 스윕의 argmax 를 held-out 에서 읽는 것은 이 저장소가 레드팀 보고서에서
스스로 금지한 행동이고 ② Train OOF 가중 품질로는 오히려 alpha=30(0.6625)이
alpha=10(0.6618)을 앞서 **두 기준이 서로 다른 값을 가리키며** ③ 격차 0.0007~0.0014 는
잡음 수준이다. **3~10 은 구분되지 않는 평탄 구간**으로 보고 배포값 3.0 을 유지한다.
`--cost-alpha` 플래그는 재현용으로만 남긴다.

### 남는 결론

산포를 줄이는 길은 이 데이터 안에 없다. 열려 있는 것은 **데이터 밖**이다 —
문항당 출력 토큰이 2.5배 안에서만 예측되는 한, 22배짜리 모델을 예산 한도 가까이
사들이는 것은 구조적으로 위험하다. 그래서 Premium 이 한도의 56% 만 쓰는 것은
**해결하지 못한 문제가 아니라 측정된 한계**다.

## 남은 격차는 어디에 있나 — 그리고 왜 회수할 수 없나

공개 Dev 880문항에서 배분기를 고정하고 입력만 참값으로 바꿔 격차를 분해했다.

| 구성 | 최종 | 해석 |
| --- | ---: | --- |
| 현행 (예측 점수 + 예측 비용) | 0.6766 | |
| **참 점수** + 예측 비용 | 0.7608 | 점수 예측의 몫 **+0.0842 (68%)** |
| 예측 점수 + **참 비용**, 마진 없음 | 0.7004 | 비용·마진의 몫 +0.0237 |
| 참 점수 + 참 비용 | 0.8009 | 상호작용 +0.0164 |

숫자만 보면 점수 예측을 고치는 것이 답이다. 실제로는 아니었다.

### 왜 아닌가 1 — `ax31 − light` 격차는 예측되지 않는다

배분기는 레벨이 아니라 **격차**로 순위를 매긴다. 그 격차의 out-of-fold 상관은:

| 격차 | 2PL 차분 (현행) | 격차 직접 회귀 | 독립 레벨 차분 |
| --- | ---: | ---: | ---: |
| `ax31 − light` | −0.008 | **+0.014** | +0.014 |
| `think − ax31` | +0.225 | **+0.342** | +0.342 |

`ax31 − light` 는 **세 방법 모두 0 근처**다. 모형의 결함이 아니라 데이터의 성질이다.
그리고 **Fast·Balanced(가중 0.7)는 전부 이 결정**이다 — 거기서 라우터는 어떤 모형을
써도 사실상 무작위로 고른다. (격차가 0이 아닌 문항이 25.1% 뿐이기도 하다.)

*(직접 회귀와 독립 레벨 차분이 소수점까지 같은 것은 정상이다 — ridge 는 선형이라
`ridge(Y_b) − ridge(Y_a) = ridge(Y_b − Y_a)` 로 같은 연산이다.)*

### 왜 아닌가 2 — 예측되는 격차를 선명하게 쓰면 손해다

`think − ax31` 은 직접 회귀가 +0.225 → **+0.342** 로 확실히 낫다(상위 10% 의 실제
격차가 0.236 → 0.467). 2PL 뼈대는 두고 think 격차만 이 예측으로 갈아 끼워 봤다.

| 구성 | CV 평균 | 시드 변동폭 | Δ vs 현행 |
| --- | ---: | ---: | ---: |
| 현행 2PL | 0.6460 | 0.0422 | — |
| think 격차 ×0.5 | 0.6473 | 0.0438 | +0.0013 (1.7×SE) |
| think 격차 ×1.0 | 0.6350 | 0.0448 | −0.0110 |
| think 격차 ×1.5 | 0.5672 | **0.1291** | −0.0788 |
| 양쪽 격차 교체 | 0.5970 | 0.0430 | **−0.0490 (25×SE)** |

**격차를 선명하게 할수록 라우팅이 나빠진다.** 선명한 격차는 think 를 더 공격적으로
사들이게 하고, think 는 22배짜리라 예산이 터진다(×1.5 에서 변동폭이 3배).
×0.5 의 +0.0013 은 1.7×SE 로 D21 문턱 미달이라 채택하지 않는다.

### 왜 아닌가 3 — 특성·정규화도 천장이다

점수 쪽 특성은 한 번도 탐색한 적이 없어 마지막으로 스윕했다. 이번에는 대리지표가
아니라 **라우팅 점수로 직접** 쟀다 (계열 편향 산포에서 얻은 교훈).

| 구성 | CV 평균 | Δ vs 현행 |
| --- | ---: | ---: |
| word512 a=3 (현행) | 0.6460 | — |
| word512 a=1 | 0.6462 | +0.0002 (0.2×SE) |
| word512 a=10 | 0.6321 | −0.0139 |
| word512 a=30 | 0.6434 | −0.0026 |
| word1024 a=3 | 0.6466 | +0.0006 (**0.0×SE**) |
| word512 + 문자 3~5gram a=3 | 0.6342 | −0.0118 |
| word512 + 문자 3~5gram a=10 | 0.6441 | −0.0019 |

**어느 것도 현행을 넘지 못한다.** 한국어·코드 형태를 잡아 줄 것으로 기대한 문자
n-gram 은 오히려 해롭고(−0.0118), 명목 최고인 word1024 는 쌍대 SE 가 0.0227 로
0.0×SE — 잡음이다.

### 결론 — 이 라우터는 예측 한계가 아니라 예산 한계에 묶여 있다

`+0.0842` 는 **실현된 0/1 결과**를 준 값이라 clairvoyance 다. 확률을 완벽히 맞혀도
도달할 수 없고, 이 저장소가 D29 에서 저지른 착각과 같은 종류다. 실제로 회수 가능한
양은 그보다 훨씬 작으며, 위 두 측정은 **그 작은 양조차 쓰려면 돈이 든다**는 것을 보인다.

점수 모형은 절대 예측력이 낮지만(레벨 OOF 상관 0.33~0.38) 그것이 미숙함의 증거는
아니다. IRT·GRM·인코더 이식·앙상블·격차 타깃·잔차 헤드 **여섯 계열이 모두 기각**됐고
특성·정규화 스윕도 천장이다. 실패 방식이 전부 같다 — 모델별 자유도를 늘리면 예산을
더 쓰고 더 흔들린다.

### ★ 위 결론의 정정 — 병목은 표현이지 데이터 양이 아니다

한때 이 절은 "남은 여지는 더 많은 학습 데이터뿐"이라고 적었다. **직접 재보니 틀렸다.**

`score` 는 2~4회 생성의 평균이라 라벨이 시끄러울 것으로 의심했으나, 표본 잡음은
작다. `s = X/N`, `X ~ Bin(N,p)` 에서 `E[s(1-s)] = p(1-p)(1-1/N)` 이므로 잡음 분산을
p 를 몰라도 추정할 수 있다.

| 대상 | 관측 분산 | 표본 잡음 | 신호 비율 | 예측 상관 상한 |
| --- | ---: | ---: | ---: | ---: |
| light / ax31 / think 레벨 | 0.213 / 0.196 / 0.133 | 0.025 / 0.021 / 0.019 | 88 / 90 / 86% | 0.94 / 0.95 / 0.93 |
| **`ax31 − light` 격차** | 0.1267 | 0.0459 | **63.8%** | **0.798** |
| `think − ax31` 격차 | 0.1852 | 0.0398 | 78.5% | 0.886 |

**`ax31 − light` 는 신호가 63.8% 실재하는데 우리가 달성한 상관은 +0.014 다.**
상한 0.798 대비 사실상 0 이다. "어느 문항에서 ax31 이 light 를 이기는가"는 실재하는
정보이고(신호 sd 0.284), 우리 특성이 못 잡을 뿐이다.

데이터 양도 아니다. 학습 문항 수를 바꿔 재면 352 → 704 → 1,056 → 1,408 에서
think 격차 상관이 +0.144 → +0.192 → +0.198 → +0.131 로 **증가 추세가 없다.**

그리고 이 쌍에는 앞의 "예산 한계" 논증이 적용되지 않는다. 그 논증은 22배짜리
`think` 에 대한 것이고, **`ax31` 은 2.1배라 Fast 에서도 20% 안팎을 감당할 수 있다.**
지금 그 20% 를 사실상 무작위로 고르고 있다.

### 그 개선의 값어치 (측정)

격차 예측 상관 `r` 을 달성했을 때의 최종 점수. think 예측·비용 모형·마진은 전부
현행 그대로 두고 `ax31 − light` 격차 예측만 품질 `r` 로 치환해 측정했다.

| r | 최종 | Δ | fast | balanced | premium |
| ---: | ---: | ---: | ---: | ---: | ---: |
| 0.014 (현행) | 0.6766 | — | 0.6452 | 0.6852 | 0.7099 |
| 0.2 | 0.6844 | +0.008 | 0.6538 | 0.6951 | 0.7144 |
| 0.3 | 0.6937 | +0.017 | 0.6640 | 0.7040 | 0.7230 |
| 0.4 | 0.7021 | +0.026 | 0.6719 | 0.7140 | 0.7305 |
| 0.6 | 0.7146 | +0.038 | 0.6811 | 0.7298 | 0.7440 |
| 0.798 (상한) | 0.7236 | +0.047 | 0.6911 | 0.7395 | 0.7509 |

**`r ≈ 0.31` 이면 주최측 `hash-regex`(0.6954)와 같아진다.**

단 낙관은 금물이다. **같은 특성이 `think − ax31` 에서는 +0.342 를 낸다.** 즉 특성이
일반적으로 약한 것이 아니라 **`ax31 − light` 구분이 특별히 어렵다.** 같은 모델
계열의 크기 차이라 "작은 쪽이 간신히 실패하는 지점"을 가려야 하기 때문으로 보인다.
표현을 바꾸면 얼마나 오를지는 **미지수이며, 시도해 봐야 안다.**

## 측정 후 기각한 것

이 저장소의 규칙은 "가정이 아니라 측정으로 정한다" 이므로 기각한 것도 적는다.
전부 `tools/train_lpb.py --predictor grm` 등으로 재현할 수 있다.

| 시도 | grouped CV 결과 | 공개 Dev | 판정 |
| --- | --- | --- | --- |
| **GRM(5수준 등급반응) + μ/σ 헤드** | **+0.0693 (2.9×쌍대SE)**, MAE 0.3042 vs 0.3384, 시드 변동폭 **0.0006 vs 0.0833** | **0.6715 (−0.0107)** | **기각** |
| 능력 사후요약(EAP) 회귀 amortization | −0.0847 | — | 기각 |
| 모델별 잔차 헤드 `r_m(x)` | −0.0580 (11.6×SE) | — | 기각 |
| 2PL MML + 예측 헤드 (`encoder.py` 충실 이식) | −0.0480, 변동폭 0.1617 | — | 기각 |
| 해시 차원 앙상블 (512/768/1024 평균) | +0.0001 (0.2×SE) | — | 기각 |
| 정규화 앙상블 (alpha 1/3/10 평균) | −0.0002 (0.5×SE) | — | 기각 |
| 차원×정규화 앙상블 (9개 평균) | **−0.0009 (5.3×SE)** | — | 기각 |

앙상블이 무효인 이유는 2PL 이 **이미 저분산 추정기**이기 때문이다 — 애초에 독립 회귀를
이긴 근거가 시드 변동폭 0.0011 대 0.0230 이었다. 평균낼 분산이 남아 있지 않고,
9개를 모두 평균내면 오히려 편향이 커져 5.3×SE 로 **유의하게 나빠진다.**

★ **GRM 건은 교차검증 지표 자체의 결함을 드러냈다.** GRM 은 CV 에서 크게 이겼는데
Dev 에서 졌다. 원인은 모형이 아니라 **지표**다 — 예산을 넘긴 등급은 0점이므로,
**승급을 거의 하지 않는 예측기는 예산을 넘길 수 없어서 "더 좋고 더 안정적"으로 보인다.**
실제로 GRM 구성은 `axk1-think` 를 **한 번도 선택하지 않았고** Premium 이 한도 4.0 중
1.69 만 쓰고 끝났다. MML 이 모집단 능력에 맞춰 item 을 보정하면서 `axk1-think` 의
변별도가 1.63 (다른 둘은 3.83·4.73) 으로 낮게 잡혔고, 그래서 기대점수가 `ax31` 을
거의 넘지 못해 배분기에 살 것이 남지 않았다.

교훈 두 가지를 남긴다. ① **예측 정확도(MAE)가 오르는 것과 라우팅 점수가 오르는 것은
다른 사건이다** — 배분기는 절대 수준이 아니라 **모델 간 격차**로 순위를 매긴다.
② **CV 지표에 0점 규칙이 들어 있으면 소극적인 정책이 과대평가된다.** 다음에 예측기를
비교할 때는 예산 초과 이벤트와 품질을 분리해서 봐야 한다.

## 규칙 준수

- 선택에 사용하는 정보는 **프롬프트 내용과 등급뿐**입니다.
- `episode_id`, `split`, `challenge_id`, 입력 순서를 읽지 않습니다.
  특성 해싱과 동률 처리에 쓰는 키는 모두 프롬프트 내용에서 계산합니다.
- 파이썬 `hash()` 는 프로세스마다 salt 가 달라 재실행 시 다른 결과를 낼 수 있으므로
  사용하지 않고 `zlib.crc32` 를 씁니다.
- 등급별 예산 배분은 배치 전체를 대상으로 하지만, ID·순서에는 불변입니다.
  `tests/test_lpb_router.py` 가 ID 치환·순서 셔플·반복 실행 결정성을 검사합니다.
- 네트워크를 사용하지 않고 실행 중 아무것도 내려받지 않습니다.

## 제출 절차

`docs/SUBMISSION.md` 는 **코드 커밋 → 이미지 빌드·push → JSON 커밋** 순서를 요구한다.
`submission-ossp-skt.json` 은 `tools/make_submission_metadata.py` 가 생성한다.
레지스트리 다이제스트는 push 후에만 존재하므로 인자로 받는다.

```console
# 1) 라우터 코드 커밋을 확정한 뒤 그 커밋에서 이미지를 빌드
docker build --pull --platform linux/arm64 --provenance=false --sbom=false \
  --file container/Dockerfile --tag <registry>/<name>:submission .

# 2) 공개 레지스트리에 push 하고 전체 다이제스트를 확인
docker push <registry>/<name>:submission
docker inspect --format '{{index .RepoDigests 0}}' <registry>/<name>:submission

# 3) JSON 생성 (현재 HEAD 를 commit_sha 로 기록, 작업 트리가 깨끗해야 함)
python3 tools/make_submission_metadata.py \
  --image-digest '<registry>/<name>@sha256:...'
python3 tools/validate_technical_submission.py

# 4) 이 JSON 만 담은 커밋을 따로 만들고, 그 커밋의 스냅샷 URL 을 결과보고서에 기재
```

## 자원 한도 검사

`tools/check_runtime.py`, 공개 Train+Dev 전체 2,640문항, `linux/arm64` 이미지,
CPU 2 · 메모리 2 GiB · 프로세스 32 · 네트워크 없음 · 읽기 전용 루트.

| 등급 | 실행 시간 | 한도 | 결과 |
| --- | ---: | ---: | --- |
| Fast | 31.7초 | 90초 | PASS |
| Balanced | 30.4초 | 90초 | PASS |
| Premium | 30.8초 | 90초 | PASS |

측정은 x86_64 호스트에서 arm64 를 에뮬레이션한 값이므로 공식 Apple Silicon 장비의
네이티브 실행보다 **느린 쪽**입니다. 네이티브(x86, 컨테이너 없음) 참고값은 2,640문항
등급당 2.2~2.4초입니다.

`tools/check_runtime.py` 자체는 POSIX 전용(`fcntl`)이라 Windows 개발 환경에서 직접
실행할 수 없습니다. 위 수치는 같은 이미지·같은 입력·같은 자원 플래그로 `docker run` 을
직접 호출해 측정했고, 출력은 공식 파서(`ossp_router.protocol.load_submission`)로
검증했습니다. 이전에 WSL 에서 공식 하네스를 돌렸을 때는 `"passed": true` 였습니다
(당시 37.3 / 35.1 / 39.9초). **공식 환경의 최종 판정은 운영자 실행을 따릅니다.**
